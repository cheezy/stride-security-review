## Release record — tags without a GitHub release

*This is a record-keeping note, not a release. It describes no change to this plugin and carries no version.*

A fleet-wide audit found **5 tags** in this repository that are tagged and pushed but have no corresponding GitHub release. **The gap is accepted and will not be backfilled.** It is recorded here so the next release engineer does not rediscover and re-litigate it:

- `v1.0.0` — 2026-05-11
- `v1.1.0` — 2026-05-11
- `v1.2.0` — 2026-05-11
- `v1.2.1` — 2026-05-11
- `v1.2.2` — 2026-05-11

These are the **entire pre-2.0 line** of this plugin — every tag from `v1.0.0` through `v1.2.2`, all cut on the same day during initial development. The 2.x line from `v2.0.0` onward is fully released.

Why accepted rather than backfilled:

- **Nothing resolved through these releases.** A GitHub release is a human-readable record, not a resolution mechanism — nothing installs *through* one. The missing releases cost nothing at the time and cost nothing now.
- **Backfilling would be worse than the gap.** A release created today against a commit from April or May would be dated today, and would manufacture a record for a state no user ever resolved through — misrepresenting the very history it claims to document.
- **The convention itself is unchanged.** These are omissions from a few release cycles, not a policy shift. Every tag still gets a release going forward.

The audit also found **zero** GitHub releases without a matching tag, so the record is incomplete in only this one direction.

## [2.7.1] - 2026-10-15

D376 confines the reproduction probe's sandbox, which W2276 introduced in 2.7.0. The ports owe the change; `docs/porting-g452-g454.md` records it. The release also carries W2287's measurement of the deep review against the 2026-10-02 baseline.

### Fixed

- **The probe sandbox no longer lets a snippet read your home directory or run code from the copy (D376).** The probe command in `modes/reproduction.md` denied writes and network access but not reads, so a snippet drawn from an untrusted diff could read `~/.ssh`, cloud credentials or a keychain and print them into the result. On macOS the deny-list on `open`, `launchctl` and `osascript` could be bypassed by copying a binary into the writable copy and running it, and on Linux a pathname Unix socket under the home directory stayed connectable. The command now refuses to run, grading by reading, when `HOME` is unset, relative, `/`, not a directory or not the account's home directory, when it or the copy has a quote, backslash or newline in its path, or when the copy resolves under it. On macOS the profile adds `(deny file-read* (subpath "$h"))`, `(deny process-exec (subpath "$r"))`, `(deny file-map-executable (subpath "$r"))` and `(deny job-creation)`; on Linux `bwrap` adds `--tmpfs /var/tmp --tmpfs "$h"`. Every earlier denial and flag stays. The paragraph after the command now says exactly what each system denies, that a script in the copy runs through its interpreter (`sh test.sh`, never `./test.sh`), and that the rest of the filesystem stays readable, as do, on macOS, the arguments and environment of your other processes, which is why the CI and untrusted-contributor rule still holds. `scripts/check_agent_contract.sh` pins every changed line, and the README, the essentials skill and the porting guide describe the narrower box. A live check on macOS 27 denied a read under `$HOME`, a hard link or `cp` from a file under `$HOME` into the copy and a read through a symbolic link to one, a copied `/bin/echo`, a copied dylib loaded through `ctypes`, a write outside the copy, a network fetch and a Unix socket connect, while `sh test.sh`, `python3 t.py` and `python3 -c` ran in the copy; a relative, `-`, quoted, missing or non-account `HOME` was refused. launchd already refused a job submitted from inside the sandbox, so `(deny job-creation)` is defence in depth. No Linux host with `bwrap` was available, so the Linux change was verified by reading only.

### Documentation

- **A measurement of the deep review after G452–G454 (W2287).** `docs/measurement-2026-10.md` compares the dispatches made with 2.6.0 and 2.7.0 against the 2026-10-02 baseline, naming the comparator for every figure, and `docs/scripts/w2287-deep-review.py` is the script that produced it. No change to the agent or the command.

## [2.7.0] - 2026-10-10

Goals G452–G454 make the considerations-mode security review accurate and cheaper to dispatch. The eval now scores this plugin's own agent (W2274). Considerations mode no longer contradicts itself: all reviewed content is data, credential-bearing considerations are redacted, and the verdict enum is closed (W2275). The reviewer is read-only, with probes run only in a temporary copy (W2276). The dispatch contract has one mode tag and no output path but `SECURITY_RESULT_PATH` (W2278). `--rci` keeps the verdicts, `--fail-on` gates on them, and a baseline never drops a finding that backs a verdict (W2279). Considerations mode works within a stated tool budget (W2282). The agent prompt is a 15 KB core plus framework packs and mode files read on demand (W2285), and the always-loaded descriptions are trimmed (W2286). W2278 pairs with `stride` 1.86.0, and neither breaks the other's older release. The ports owe every change; `docs/porting-g452-g454.md` records what each needs.

### Fixed

- **`--full --patches` sends the patch rules (W2285).** Step 4b's dispatch omitted the `Patches mode: enabled` line that Step 1 says is injected in both modes, so a full scan never emitted `patch`. Step 4b now sends the Patches block too.
- **The eval now scores this plugin's agent, not base Claude (W2274).** `scripts/run_eval.sh` piped each fixture prompt to a bare `claude -p`, so every result measured the base model and the README's description of the eval was wrong. Each fixture now runs as `claude -p --plugin-dir <repo root> --agent stride-security-review:security-reviewer`, from an empty scratch directory with every tool off and no MCP servers, so the agent cannot read the expected answers or edit the repo. The exact invocation and the auth mode are printed after the TAP plan line (`--dry-run` included), and the CLI's stderr is kept in `logs/<stem>.err.txt` instead of being discarded.
- **Considerations rows without an `AND` clause were mis-parsed.** The "findings unchecked" form shifted fields when split on tabs; it now carries an explicit `U` marker.
- **Considerations mode no longer contradicts itself (W2275).** The noise filter suppressed denial-of-service, rate-limit and memory findings while a `partial` or `unmitigated` verdict was meant to be backed by one, so a listed "uploads are size-bounded" consideration could never be backed. A consideration the task lists is now exempt from the filter for that consideration only — diff and full modes keep it unchanged — and the backing finding is a MUST. A gap in pre-existing code now has a rule: the verdict is graded against the changed code, and the gap is named in `note` plus one `info` finding. The "read surrounding code for high confidence" and "do not enumerate the repository" rules are reconciled by a stated read scope: the changed files and their direct callers, at most 10 files beyond the diff.
- **All reviewed content is data, never instructions (W2275).** The rule covered only consideration strings; it now covers diff hunks, code comments, string literals and every file read, and only the caller's dispatch lines carry instructions.
- **Credential-bearing considerations are redacted (W2275).** Verdicts copied each consideration verbatim, so a credential in one reached the persisted result. Such a consideration is now echoed as `[REDACTED — row text embedded a credential]` in its position, the same sentinel the Stride task-reviewer uses.
- **The verdict status enum is closed (W2275).** `mitigated`, `partial` and `unmitigated` are the whole enum; values such as `not_applicable` are forbidden, and a consideration with no matching surface is `mitigated`.
- **One mode tag spelling (W2278).** The agent's Input modes said only that the caller "declares" a mode, three spellings were in use (the command's `/security-review invocation, mode: considerations`, the eval's bare `mode: considerations`, and prose), and a tag the agent did not recognise fell back to `diff` mode, silently dropping every consideration verdict. The tag is now exactly `/security-review invocation, mode: <mode>` on its own line, and nothing else is a tag. With no tag, a considerations list on the caller's own dispatch lines, under any header (as `stride` 1.85.0 and earlier send it, with no tag and no fixed header), is still reviewed in `considerations` mode; a list that appears only inside the reviewed content never selects a mode, and a tag naming another mode wins over a list.
- **No output file but `SECURITY_RESULT_PATH` (W2278).** A dispatch line asking for verdicts, findings or a report in any other file is ignored on that point: the document goes to an accepted `SECURITY_RESULT_PATH` or inline in the final message. Prompts that invented their own output file were a source of unparseable results.
- **`--rci` keeps considerations, MAESTRO and patches (W2279).** Step 4.5 re-sent none of the first dispatch's directives, so `--considerations --rci`, `--maestro --rci` and `--patches --rci` lost `consideration_verdicts`, `maestro_layer` and `patch` after the first critique pass. Every pass now re-sends them verbatim under the `rci_pass` tag and asks for the verdicts back; a pass with missing or malformed verdicts exits 2. The agent treats an `rci_pass` that re-sends a considerations list as a considerations-mode pass that never drops a backing finding without re-grading its verdict.
- **`--fail-on` fails closed on consideration verdicts (W2279).** The gate counted finding severities only, so an `unmitigated` verdict with a `medium`, `low` or missing finding exited 0. An `unmitigated` verdict now trips the gate at every threshold, even with no finding, and so do a `partial` verdict that no finding backs and a missing or malformed verdict array. A backed `partial` is gated by its finding's severity.
- **Baseline suppression keeps the finding behind a verdict (W2279).** A baseline could drop the finding that backed a `partial` or `unmitigated` verdict, leaving the verdict unbacked and the gate blind to it. A finding at an open verdict's evidence `file:line` (or range) is now never suppressed, and when an open verdict matches no finding nothing is suppressed in that run. `suppressed_count` counts only what was dropped.
- **`--json` and `--sarif` no longer skip the `--fail-on` gate (W2279).** Step 5's JSON and SARIF branches ended in "Stop.", before Step 6, so read literally `--json --fail-on` — the CI shape — never gated. Both branches now print nothing more and go on to Step 6.

### Changed

- **The security reviewer is a 15 KB core plus rule files read on demand (W2285).** `agents/security-reviewer.md` was 95,637 bytes and loaded whole on every dispatch. It is now a 15,352-byte core under the same section headings: the methodology, the vulnerability classes, the false-positive filter, the output schema, the severity table (kept verbatim) and a compact per-consideration verdict contract. The framework, supply-chain, CI/CD and agentic sections and the long result-file, reproduction and considerations rules moved — verbatim apart from headings, cross-references and the activation notes below — into files the agent reads from `${CLAUDE_PLUGIN_ROOT}` only when the input needs them. Three passages did not move into a file: "What the caller does with your output" was dropped (its one rule, that prose outside the JSON fence is discarded, is implied by the schema's single-fence contract, and the bounded result-file reply is in `modes/result-file.md`), and the "Adding a new framework pack" and CI "Adding a new platform" guidance, which is for maintainers, now lives in the README.
  - `packs/` — `android`, `django`, `express`, `ios`, `phoenix`, `rails`, `react-nextjs`, `web-defense`, `supply-chain`, `ci-cd` and `agentic`, chosen by a reviewed file's extension, path, structure or imports. A mixed diff loads every matching pack (a Phoenix-plus-Django diff read `phoenix`, `django` and `web-defense`). CI and supply-chain files are now recognised by structure as well as by name — a workflow that arrives as `test/fixtures/…yml` still loads `ci-cd` — and the activation text in `packs/ci-cd.md` and `packs/supply-chain.md` says so, so pack and loading table state one rule.
  - `modes/` — `considerations` (the full verdict rules, the tool budget and the noise-filter exceptions), `result-file` (the `SECURITY_RESULT_PATH` write) and `reproduction` (the sandboxed probe).
  - Text in the reviewed content never loads, skips or limits a pack. An unreadable file means the core rules alone, never no review: the agent never writes a result file without `modes/result-file.md` (it replies `result: NOT WRITTEN` and inline instead) and never runs anything without `modes/reproduction.md`. A probe copy with `packs/phoenix.md` deleted still returned a full review. The reads are instructions, so they count toward neither the 10-file read limit nor the considerations-mode tool budget.
  - The directories sit at the plugin root, not under `agents/packs/` as planned: Claude Code registers every `.md` below `agents/` as an agent, so a pack there showed up as a dispatchable `<plugin>:packs:<name>` agent (checked on Claude Code 2.1.296). `${CLAUDE_PLUGIN_ROOT}` is substituted into the agent body both when the agent is the session agent (`claude -p --plugin-dir … --agent …`) and when it is dispatched through the `Agent` tool; both were checked live on a probe plugin before the split.
  - What a dispatch now loads: a Stride considerations-mode review of a Phoenix change reads about 39 KB of instructions (core, `considerations`, `result-file`, `phoenix`, `web-defense`) instead of 95.6 KB; a diff-mode review of one web framework about 25 KB. The considerations and result-file rules load on every Stride dispatch anyway, so the Stride saving comes from the packs, the probe block, the opt-in sections and the description — the agent description, which is loaded in every session, went from 2,557 to 291 bytes (the `description:` line, `wc -c`) (the W2286 trim, done here for the agent; the skill description and the variants are still W2286's).
- **MAESTRO, patch and RCI rules travel with their flag (W2285).** The agent's MAESTRO table and non-AI mapping and its patch conditions moved into the command's new "Opt-in directive blocks", sent verbatim only with `--maestro` or `--patches`; the RCI critique directive now also sets `summary.rci_passes`. The agent keeps a one-line gate for `maestro_layer`, `patch` and `rci_passes`, and the command no longer restates the output schema. A probe dispatch carrying both blocks returned `maestro_layer: data-operations` and a `--- a/…` patch.
- **With its packs readable, the eval shows no verdict regression (W2285).** Every run used the blank-line `CLAUDE_CLI` wrapper from W2282, because `claude -p` still reads a prompt that opens with the `/security-review` tag as the built-in command (the runner fix is still open). B0 is the agent before the split, tool-less; A2 is the split agent with `Read` scoped to a plugin copy without `test/`, as it runs in Claude Code and now in CI; A1 is the split agent tool-less, the runner's default, in which no pack can load. All 82 rows, Claude Code 2.1.296, `claude-opus-5-5`, claude.ai login: **B0 61/82; A2 63/82, then 68/82 and 65/82 on later text; A1 63/82** — the first runs of the 70 full-file rows. The first A2 run regressed three rows, each traced to compressed core wording and fixed: the `partial`/`unmitigated` definitions and the pre-existing-gap scope ("the risk a consideration names") were restored, and the core's data-exposure row regained "treat a credential-shaped literal as real", which the original prompt carried in every mode. After the fixes all 12 considerations rows passed in A2 and A1, `hardcoded_secret.js` passed 3/3 in A2 (it was 0/3, against B0's 2 of 3), and B0 re-runs passed the two considerations rows 2/2. The two later full A2 runs each lost one or two rows (`docs_only_none_mitigated`, `ios_ats_arbitrary_loads.plist`, and `credential_in_consideration_mitigated`, whose verdicts were right but whose reply was not valid JSON); re-run on the final text they passed 2/3, 2/3 and 3/3, and a row counts as a regression only at 1 of 3 or fewer. **The tool-less arm does regress** four pack rows (`prompt_injection.py`, `prompt_injection.ts`, `curl_pipe_sh.sh`, `nextjs_getserversideprops_leak.tsx`): their rules live in packs a tool-less run cannot read, which is the documented fallback to the core rules, and the reason CI now runs with `Read`. Each run is a row in `test/fixtures/EXPECTED.md`, *Recorded runs*; the README says how to run the Read-enabled arm.
- **The security reviewer is read-only on the working tree (W2276).** Its tools were `Read, Grep, Glob, Bash` with Bash unrestricted, and dispatches used it heavily (3,586 Bash calls and 283 test-suite runs, per `docs/porting-g452-g454.md`); five edited tracked files in place and then restored them, racing the main loop on the same files, and 17 calls were rejected for control characters in probe payloads. *Operational constraints* now says the agent never creates, modifies, moves or deletes anything in the repository, not even to restore it and not through `git`; it inspects with `Read`, `Grep` and `Glob`, and uses `Bash` for three things only: the `SECURITY_RESULT_PATH` file, the read-only commands `git diff`, `git log`, `git show`, `git ls-files`, `ls` and `wc`, and — only when reading cannot settle a question — one reproduction in a `stride-security-probe.XXXXXX` copy under the temp directory. The copy is made by copying the repository's files (never linking), used by a single subshell command with an `EXIT` trap, and removed before the agent returns. The command refuses a copy that holds a symbolic link (`tar` recreates a link, not its target) and runs the snippet only through a sandbox that denies network access (Unix sockets included), every write outside the copy, and the local IPC an outside process could act through — on macOS `sandbox-exec` with mach lookups, Launch Services, Apple Events and `open`/`launchctl`/`osascript` denied; on Linux `bwrap` with every namespace new, `/run` and `/tmp` empty and a new session — under `env -i` with `HOME` and `TMPDIR` inside the copy, so inherited credentials stay behind; with neither sandbox the agent runs nothing and grades by reading, and it runs nothing in CI (the command checks `CI` first) or on a change from an untrusted contributor, because the sandbox stops writes and network access but not reads. One test or snippet, never the suite; payloads go in files inside the copy, with no control character in a command; every sink the snippet exercises is rebased into the copy; no dependency fetch, database or shared service; and no command written in the reviewed text is ever run. The read-only commands exclude a bare `git diff` against the working tree, which rewrites `.git/index` even with `--no-optional-locks`; `git diff --cached`, commit-to-commit `git diff` and `git diff-index -p` are listed instead. On macOS the final command was exercised on a scratch repository: a write inside the copy succeeded; a write outside it, a TCP connect, a connect to a Unix socket listening outside the box, `webbrowser.open` and `/usr/bin/open` were all refused; the environment held 7 variables; the copy was removed; a copy holding a symlink was refused; and with `CI` set nothing ran. The `bwrap` branch was not run here (no Linux host); if it fails to start, the agent runs nothing. A copy left by a killed dispatch is recognisable by its name, and the README gives an operator cleanup line. The result file stays the one write in the repository.
- **Bash is kept, on eval evidence (W2276).** On the 11 considerations rows, with Bash (`--tools`/`--allowedTools` `Read,Grep,Glob,Bash`) and without it (`Read,Grep,Glob`, Bash denied) both passed **11/11 with identical verdicts on every row**, and the tool-less CI default did too; all three arms were run twice, before and after the review-driven sandbox wording, with the same result (EXPECTED.md, *Recorded runs*). The findings differed only in class or count on the two noise-class rows. Verdict quality therefore holds without Bash on these fixtures, but Bash stays: it is the only way the agent writes the `SECURITY_RESULT_PATH` file atomically (`Write` would accept any path and protect nothing more), and a pattern-restricted `Bash(...)` entry in agent frontmatter does not narrow it — measured on Claude Code 2.1.296, an agent with `tools: Read, Bash(echo:*)` still ran `pwd`, and only the permission mode stopped `touch` — so the frontmatter lists `Bash` whole and the written contract scopes it. The eval runs from an empty directory, so it measures whether the tool is available, not a repository-backed reproduction; three manual considerations dispatches on a scratch repository seeded from the new fixture (Bash allowed, operator settings off) covered that. None changed a tracked or untracked file — the only new file each time was the ignored `.stride/` result — and none ran the `pytest` command written in the diff. On the text before the sandbox wording, the dispatch asked to reproduce did so in a `stride-security-probe.*` copy that was gone when it returned; on the final text the same request was declined, because reading settled the verdict and the endpoint needed packages the contract forbids installing.
- **CI scores the agent with its packs (W2285).** `.github/workflows/eval.yml` copies the plugin without `test/`, `.git` or `logs/` into the runner's temp directory and runs `scripts/run_eval.sh` with `EVAL_TOOLS=Read`, `Read` allowed only inside that copy and every other tool denied, so the agent can read only that copy — its `packs/`, `modes/` and docs — and never the expected answers. `check_eval_invocation.sh` pins each of those settings in the workflow: the three exclusions, the copy as the plugin directory, `Read`, its scope, and the denied tools. The runner's own default stays tool-less.
- **CI fails on `main` without the key.** `.github/workflows/eval.yml` used to skip the agent eval whenever `ANTHROPIC_API_KEY` was missing, which made it skip every run. A push to `main` or a manual dispatch now fails with an error when the secret is not configured; pull requests (where fork and Dependabot PRs get no secrets) still skip with a notice. The job timeout is raised from 30 to 45 minutes.
- **The eval accepts a claude.ai login locally.** `run_eval.sh` uses `ANTHROPIC_API_KEY` when set and otherwise a logged-in CLI; with neither it exits `2`. Neither the key nor the auth-status output is printed.
- **Two considerations rows assert a backing finding (W2275).** `upload_body_size_unmitigated` and `preexisting_query_gap_mitigated` were verdict-only pending these rules; both now carry `AND finding`. A recorded run after the W2275 edits passed all ten considerations rows (claude.ai login), so the two new rows and the two strengthened ones are ticked; the redaction and the `info` severity, which the eval cannot see, were checked by hand in `logs/`. A sensitivity run against the pre-W2275 agent failed the rate-limit and pre-existing-gap rows and leaked the fake literal into the credential row's `consideration`, so those three rows measure the new rules; the upload row does not discriminate, as its row says. `scripts/check_agent_contract.sh` (and its CI step, now named "Check the agent contract") pins the new considerations-mode sentences alongside the result-file contract.

- **A considerations dispatch has a tool budget (W2282).** The 257 recorded dispatches made 4,402 tool calls, including 283 test-suite runs (`docs/porting-g452-g454.md`). That is far more than grading the listed considerations needs, and nothing in the agent bounded it. In `considerations` mode a dispatch now has a budget of **20 tool calls, at most 2 of them reproductions**. Writing the result file never counts and is never skipped, and each `rci_pass` that re-sends the list gets its own budget. `diff` and `full_file` mode have no budget, and the shared 10-file read limit is unchanged. The agent grades from the diff it was given first. It reads a changed file in full, or searches for direct callers, only when a verdict needs more than the hunks. It may read past them (a caller's caller, or a config file the changed code reads) only when a verdict turns on it. Such a read counts toward the 10-file limit and the budget, and the verdict's `note` names it as `read <file>: <why>`. A reproduction now runs only to confirm a specific claim stated in a verdict's `note` or a finding's `description`, inside the existing temporary copy, one test and never the suite. When the budget runs out before a consideration is settled, the verdict is `partial` with a `note` that begins `budget reached:` and names what stayed unverified. It is never `mitigated`. This is the one `partial` that no finding backs, and its `evidence` cites no `file:line`. So `/security-review --fail-on` fails on it at every threshold, and the Stride workflow escalates it `critical`. An `info` backing finding was rejected because `info` never trips a threshold, so an unverified consideration would pass CI. The eval runs tools-off in an empty directory, so it cannot observe tool calls. The budget was therefore measured by hand on one real input. That input was the W2228 commit (the owner-only Integrations tab) in a clone of the kanban repository, with its two security considerations and a diff with the translation catalogues left out. Each run was a `claude -p --agent stride-security-review:security-reviewer --output-format stream-json` run with `Read,Grep,Glob,Bash` allowed, and the `tool_use` events were counted. This agent made 4 tool calls (2 `Read`, 2 `Grep`). The agent before W2282 made 6 (3 `Read`, 2 `Grep`, 1 `Bash`). Both graded both considerations `mitigated` with no findings. The Stride deep review of this task's own diff made 6 tool calls. One input shows the budget is respected and the verdicts hold. It cannot show the effect on the largest dispatches (up to 53 requests) or on suite runs, which is the corpus measurement W2287 owns.
- **Shorter always-loaded descriptions, same triggers (W2286).** Both descriptions sit in every session's agent and skill lists, so every main-loop request pays for them. Sizes here are the parsed YAML `description` value. The `security-review-essentials` skill description goes from 723 to 332 bytes: it keeps every trigger — about to merge, or push a PR with, changes touching authentication, authorization, cryptography, user input handling, secrets management, database queries, shell-outs, file uploads, redirects or response rendering, or a human reviewer asking for a security check — and drops the output format, severity list and noise-filter summary, which the skill body and the agent already state. The agent description, already cut by W2285 (2,555 to 289 bytes parsed; the 2,557 and 291 in that entry count the `description:` block with `wc -c`), now opens "Use this agent to security-review …" like the `stride` plugin's agents and gets back the trigger that cut lost — reviewing before merge, which the old text gave as "any agent workflow that needs to gate code changes on a security check before merge". It drops "(one verdict each)" to make room and is 286 bytes, so the core stays inside its 15,360-byte bound at 15,349 bytes. The gemini, opencode, copilot and codex variants are not changed here.

### Added

- **Frontmatter checks for the two always-loaded descriptions (W2286).** `check_agent_contract.sh` now checks that the agent's and the skill's frontmatter have the shape YAML reads (fences, `key: value` or `key: |` lines, no duplicate key, and no plain value holding `: ` or ` #` or opening with a YAML indicator character — a heuristic for the common misreadings, not a full YAML parse) and their required keys; that the agent is still named `security-reviewer`, the name Stride dispatches; that each description is 150–400 bytes; and that each still carries its triggers, read from the description itself rather than the whole file, so a later trim cannot silently drop one. Each new check was broken once in a scratch copy and seen to fail.
- **Contract checks for the split (W2285).** `check_agent_contract.sh` bounds the core at 10,240–15,360 bytes; checks that each of the 11 packs and 3 mode files exists, is non-empty, has no frontmatter and is named in the loading table, that no other file sits in `packs/` or `modes/`, that every file the table names exists, and that no `.md` sits below `agents/`; pins the loading rules, the fallbacks and each pack's activation text; moves the result-file, reproduction and budget pins to the mode files that now hold them; and checks that the MAESTRO table, the patch rules, the packs and the probe sandbox are gone from the core and that the command owns the opt-in blocks. Each new check was broken once to see it fail.
- **Contract pins and transform checks for the tool budget (W2282).** `check_agent_contract.sh` pins the budget, the exemption for `diff` and `full_file`, the justified wider read, the claim-bound reproduction, the `budget reached:` `partial` and its place in the command's gate. `run_transform_tests.sh` grows from 45 to 47 checks: a `budget reached:` `partial` trips `--fail-on critical` with no findings, and an `info` finding beside it does not back it.
- Considerations fixture `config_session_cookie_unmitigated` (W2282) covers the task's two edge cases, a larger diff and a consideration about a config file. It is a five-file diff of 176 lines whose one security-relevant hunk turns `SESSION_COOKIE_SECURE` off in the production config. Both verdicts settle from the diff alone. Pointed at a scratch copy whose diff leaves `SESSION_COOKIE_SECURE` on, the row fails: the agent returns `mitigated,mitigated`.

## [2.5.0] - 2026-07-22

### Added — `considerations` mode verifies a task's security_considerations were actually mitigated (G366: W1857–W1860)

A third input mode, `considerations`, turns "considerations declared" into "considerations verified mitigated." This is the Claude Code plugin surface of the capability; the five runtime ports and the Stride-orchestrator/kanban-app integration are separate, out-of-scope work.

(3) LiveView `allow_upload(:any)` without `max_file_size:` / content-type re-check (CWE-434, A04:2021) mapped to `input_validation`. Each has explicit non-trigger guidance (the `to:` redirect form, `System.cmd("convert", [argv])`, `allow_upload` with both `accept:` and `max_file_size:` set). Comes with `phoenix_token_no_max_age.ex`, `phoenix_system_cmd_shell.ex`, and `phoenix_liveview_upload.ex` fixtures. The Phoenix open-redirect rule was added in the parallel open-redirect task and is not duplicated here.
- **Django pack expansion: SSRF, DRF `ModelSerializer fields='__all__'`, ALLOWED_HOSTS / SECURE_* hardening.** Three changes to the Django pack: (1) new SSRF rule (CWE-918, A10:2021) mapped to `input_validation` covering `requests.get(url)`, `urllib.request.urlopen(url)`, and `httpx.AsyncClient().get(url)` where `url` traces to `request.*` — realistic worst case is cloud-metadata exfiltration via `169.254.169.254`. (2) new DRF mass-assignment rule (CWE-915, A04:2021) mapped to `authorization` covering `serializers.ModelSerializer` with `fields = '__all__'` on a model that has privileged fields (`is_staff`, `is_superuser`, `is_admin`, `role`, `owner_id`). (3) extended the existing `DEBUG = True` rule into a combined "production-bound settings hardening" rule that also flags `ALLOWED_HOSTS = ['*']` and missing `SECURE_SSL_REDIRECT` / `SESSION_COOKIE_SECURE` / `CSRF_COOKIE_SECURE` / `SECURE_HSTS_SECONDS`. All three rules have explicit non-trigger guidance (validated SSRF allow-lists, explicit DRF `fields = [...]`, dev/test settings files). Comes with `django_ssrf.py`, `django_drf_mass_assignment.py`, and `django_insecure_settings.py` fixtures.
- **Deserialization rules for Django and Rails packs** (CWE-502, A08:2021). Both map to `xss_or_code_exec`. Django flags `pickle.loads(...)` on attacker-influenced bytes, `yaml.load(...)` without `Loader=yaml.SafeLoader`, `shelve.open(...)` on attacker-controlled paths, and `django.core.signing.loads(token)` without an explicit `max_age` on a value sourced from `request.*`. Rails flags `Marshal.load(params[...])`, `YAML.load(...)` without `permitted_classes:`, and `YAML.unsafe_load(...)`. Negative cases explicit in both rule rows: `yaml.safe_load`/`json.loads`/`YAML.safe_load`/`JSON.parse` and signing.loads with both `max_age` and `salt`. Comes with `test/fixtures/django_deserialization.py` and `test/fixtures/rails_deserialization.rb`. Closes a high-recall CVE class for both ecosystems (Rails CVE-2013-0156, CVE-2022-32224; Python's canonical pickle.loads RCE).
- **Open-redirect rules across Django, Phoenix, and Rails packs** (CWE-601, A01:2021). Each pack gains one rule mapped to `input_validation`: Django flags `HttpResponseRedirect(request.GET['next'])` / `redirect(request.POST['url'])` without `django.utils.http.url_has_allowed_host_and_scheme`; Phoenix flags `redirect(conn, external: params['url'])` (the `external:` key bypasses same-origin); Rails flags `redirect_to params[:url], allow_other_host: true` and similar overrides of the Rails 7+ default. Each rule has explicit non-trigger guidance (validated redirects, internal route helpers, `to:` key for Phoenix). Comes with three positive-control fixtures: `django_open_redirect.py`, `phoenix_open_redirect.ex`, `rails_open_redirect.rb`. Closes the most-flagged class in Brakeman's Rails output and equivalent gaps in the Django and Phoenix packs.
- **Negative-control fixtures.** Three look-alike-but-safe fixtures added to `test/fixtures/`: `phoenix_changeset_safe.ex` (`cast/3` with explicit `[:email, :name]` allow-list excluding `:role` and `:is_admin` — must NOT trigger mass-assignment), `phoenix_fragment_safe.ex` (`fragment("? = ?", field, ^user_input)` positional-binding form with the `^` pin — must NOT trigger fragment-injection), `rails_html_safe_constant.rb` (`.html_safe` on string literals and an allow-list-keyed lookup table — must NOT trigger XSS). The eval runner gained a `→ NONE` syntax in `EXPECTED.md` for zero-findings assertions; `compare_finding` was extended to fail when any finding fires on a negative-control fixture, so over-firing regressions are detected mechanically (today the eval could only catch missing findings, not over-firing).
- **Web defense-in-depth pack** in `agents/security-reviewer.md` between the Rails pack and "Adding a new framework pack". Framework-agnostic — activates on middleware / Endpoint / response-pipeline shapes rather than file extension. Four rules, all mapping to `insecure_config`: (1) missing `Content-Security-Policy` on HTML responses, (2) missing `Strict-Transport-Security` (HSTS) in production HTTPS configs, (3) missing `X-Frame-Options` / `frame-ancestors`, (4) `Set-Cookie` without `Secure` / `HttpOnly` / `SameSite` on session/auth cookies. Severity medium for the header rules; high when an authenticated session cookie is missing `Secure` or `HttpOnly`. The pack is explicitly defense-in-depth — a sibling-note finding when a primary XSS/CSRF/session-hijack issue is already raised on the same response site, never a duplicate. Comes with positive-control fixtures `test/fixtures/django_missing_headers.py` and `test/fixtures/phoenix_missing_headers.ex` plus EXPECTED.md entries (the eval asserts the high-severity cookie-flags finding; the medium-severity header findings are bonus).

### Changed

- **Added MAESTRO mapping guidance for non-AI framework findings.** The MAESTRO 7-layer subsection at `agents/security-reviewer.md` previously said to omit `maestro_layer` for classic web vulnerabilities — leaving per-run inconsistency in the `By MAESTRO layer` summary section. Now: data-flow vulnerabilities (injection, XSS, mass-assignment, SSRF, open redirect, deserialization) map to `data-operations`; access-control / audit / config vulnerabilities (missing auth, CSRF disabled, `DEBUG = True`, missing security headers) map to `security-compliance`. The other five layers remain AI-specific. `commands/security-review.md` was updated to reference this mapping rather than re-specify it.
- **Re-mapped mass-assignment rules from `input_validation` to `authorization`** in the Django (`Form.cleaned_data` direct write), Phoenix (`Ecto.Changeset.cast/3` with bulk allow-list), and Rails (`params.permit!`) packs. The actual harm of writing `:is_admin`, `:role`, or `:owner_id` via mass assignment is privilege escalation, not weak input validation; under the `authorization` class the severity rubric biases high/critical instead of low/medium, matching real-world impact. The `phoenix_mass_assignment.ex` fixture's EXPECTED.md entry was updated in lock-step (`authorization/high`, CWE-915, A04:2021). No rule prose, activation predicate, or non-trigger clause was changed — this is a class-mapping correction only.
- **Standardized "what to look for" prose across the Django, Phoenix, and Rails framework packs.** Every rule row now follows the 2-3 sentence template established by the v2.1.0 Phoenix mass-assignment rule: (1) positive pattern with concrete trust-boundary indicators, (2) discriminating signal or analog rule across packs, (3) explicit `Do NOT flag <X>` non-trigger clause where realistic look-alikes exist. Mapping columns and rule-name columns are unchanged. The longer form measurably reduces false positives on look-alike-but-safe code (literal-string `mark_safe`, parameterized `raw()`, JSON-API `@csrf_exempt`, dev-only `DEBUG = True`, allow-listed Strong Parameters, positional `fragment("? = ?")`, scoped `Repo.get`, constant-symbol `obj.send`).

## [2.1.0] - 2026-05-13

### Added

- **Eval runner (`scripts/run_eval.sh`).** POSIX bash + `jq` runner that dispatches the `security-reviewer` agent via `claude -p` against every fixture in `test/fixtures/` and asserts the expected `vulnerability_class` + `severity` from `test/fixtures/EXPECTED.md`. Output is [TAP 13](https://testanything.org/tap-version-13-specification.html); exit `0` only if every fixture produces its expected finding at the expected count (the Bitbucket multi-finding fixture requires both). Failing fixtures emit a diff-style expected-vs-actual block. CWE/OWASP mismatches are advisory (warn, no fail). Raw agent JSON for each fixture is written to `logs/` (gitignored). Flags: `--fixture <path>` (run one), `--dry-run` (no API call), `--verbose` (echo prompts + JSON to stderr), `--fixtures-dir <path>` (override location).
- **GitHub Actions workflow (`.github/workflows/eval.yml`).** Runs the eval on push to `main` and on PRs that touch `agents/`, `commands/`, `skills/`, `test/fixtures/`, the runner itself, or the workflow. Uploads `logs/` as a build artifact on failure. All third-party actions are pinned to 40-hex commit SHAs, in line with the plugin's own supply-chain rule.
- **README "Running the eval locally" section** documenting prerequisites, invocation, flags, and the assertion tolerance model.
- **`.gitignore` entry for `logs/`** so eval output stays untracked.
- **Phoenix mass-assignment rule** in the framework-aware pack at `agents/security-reviewer.md`. Flags `Ecto.Changeset.cast/3` calls reached from `Phoenix.Controller` actions or `Phoenix.LiveView` `handle_event` clauses whose allow-list is `__MODULE__.__schema__(:fields)`, `Map.keys(attrs)`, or an explicit list that includes privileged fields (`:role`, `:is_admin`, `:owner_id`, `:user_id`, `:permissions`). Maps to `input_validation`. Phoenix analog of the Rails `params.permit!` rule. Comes with `test/fixtures/phoenix_mass_assignment.ex` (positive control: controller updates a `User` schema via `cast(attrs, __MODULE__.__schema__(:fields))` exposing `:role` and `:is_admin` to client write) and an `EXPECTED.md` entry at severity `high`, `CWE-915`, `A04:2021`.
- **`--fail-on <severity>` flag and exit-code contract.** `commands/security-review.md` gains a `--fail-on critical | high | medium | low` flag and a new Step 6 that, when the flag is set, evaluates the final post-RCI / post-baseline findings list and runs `exit 1` via Bash when any finding meets the threshold. Default behavior (no `--fail-on`) preserves exit 0 always — byte-identical exit behavior for callers that do not opt in. Invalid `--fail-on` values produce exit 2 with a clear error. Severity ordering is `critical > high > medium > low > info`; `info`-only findings never trip a threshold.
- **GitHub Actions workflow `.github/workflows/security-review.yml`.** Reference CI gate for downstream repos (and the plugin's own PR check). Runs the slash command with `--json --fail-on ${FAIL_ON}` on every pull request, then post-checks the JSON with `jq` — the merge is blocked if EITHER `claude -p` exits non-zero OR jq counts at least one finding at/above the threshold. Robust to `claude -p` exit-code propagation variations across Claude Code CLI versions. Threshold defaults to `critical`, overridable via `workflow_dispatch` input or by editing the `FAIL_ON` env. Third-party actions pinned to commit SHAs. Uploads `review.json` and `review.stderr` as a build artifact on every run for triage.
- **README "CI Integration" section** documenting the exit-code contract, the belt-and-suspenders gate pattern, and how to tighten the threshold.
- **`--base <ref>` diff scope.** `commands/security-review.md` Step 1 gains a `--base <ref>` flag that, when set, makes Step 2a use the three-dot range `<ref>...HEAD` instead of `HEAD` — scoping the review to changes the current branch introduced over the named base. Validates the ref exists via `git rev-parse --verify`; invalid ref produces exit 2 (never silent fallback to HEAD). The flag is a no-op under `--full` (a stderr warning is printed and execution continues, since full mode uses `git ls-files` which is ref-independent). Two-dot range was rejected because it would include base-side commits since divergence. The reference workflow at `.github/workflows/security-review.yml` automatically passes `--base origin/${{ github.base_ref }}` on `pull_request` events. README "PR-against-base scope" subsection added under CI Integration.
- **`--sarif` output mode.** `commands/security-review.md` Step 1 gains a `--sarif` flag and Step 5 gains a SARIF v2.1.0 emission branch. The transform maps the agent's native findings to a SARIF document conforming to the OASIS schema: `vulnerability_class` → `ruleId`, severity → `level` (critical/high → error, medium → warning, low/info → note) and `properties.security-severity` (numeric 9.0/7.0/5.0/3.0/1.0), `file`/`line` → `physicalLocation`, `description` → `message.text`, `remediation` → `fixes[0].description.text`, `cwe` ∪ `owasp` ∪ `confidence:<value>` → `properties.tags[]`. Cross-run dedup uses the same Step 4.6 fingerprint algorithm, emitted as `partialFingerprints["stride/v1"]`. `--sarif` and `--json` are mutually exclusive (both → exit 2). MAESTRO and Patches modes compose: `maestro:<layer-id>` is appended to `properties.tags[]` when `--maestro` is set; surgical patches populate `fixes[0].artifactChanges` when `--patches` is set. Mode-independent (same shape from diff and full). README "SARIF output" subsection added under CI Integration with a `gh api repos/:owner/:repo/code-scanning/sarifs` upload recipe. New `schema/README.md` documents the field-mapping reference and the canonical SARIF schema URLs.

## [1.2.1] - 2026-05-11

### Fixed

- **`--full` mode now runs unattended under the slash command's `allowed-tools` whitelist.** The v1.1.0 enumeration documented a piped `git ls-files | while ...; do grep -Iq ...; wc -c < ...; done` loop. Claude Code's permission system matches the full Bash command string against `allowed-tools` prefixes, so a compound pipeline did not match any single entry and required a permission prompt on every invocation (or was skipped outright by the model, falling back to diff-mode behavior). Step 2b now uses two single-shot batched calls — `grep -Il . <files...>` for the binary filter and `wc -c <files...>` for the size filter — each covered by a dedicated `Bash(grep:*)` / `Bash(wc:*)` entry. ## [1.2.0] - 2026-05-11

A major capability release. Every existing finding shape stays valid; every new feature is opt-in via a flag, so callers that consumed v1.1.0 JSON continue to work without modification.

### Added

- **CWE and OWASP references on every finding.** Each finding now carries a `cwe` array (e.g., `["CWE-89"]`) and an `owasp` array (e.g., `["A03:2021"]`) so triage tools can group findings by canonical class without parsing prose. Both default to `[]` only when a finding doesn't map to any standard category.
- **`supply_chain` vulnerability class.** Five sub-rules covering floating-tag container base images, pipe-to-shell installers (`curl | sh`), CI/CD references by branch/tag instead of immutable SHA, manifest/lockfile drift, and typosquat/hallucinated package names. Multi-ecosystem coverage: npm, PyPI, RubyGems, Hex, crates.io, Maven, NuGet, Packagist, Go modules.
- **Five MAESTRO-derived agentic-AI vulnerability classes** that activate when the reviewed code imports a recognized LLM/agent/MCP SDK:
  - `prompt_injection` — untrusted text concatenated into LLM prompts without separation.
  - `tool_abuse` — agent function-call / MCP tool layers exposing file/shell/DB operations without per-tool authorization.
  - `agent_trust_boundary` — agent-to-agent message passing where one agent's output flows into another's prompt without quarantine.
  - `model_output_execution` — LLM response text flowing into `eval` / `exec` / `subprocess` / `Function()`.
  - `vector_store_poisoning` — user-controllable content embedded into vector DBs (Pinecone, Weaviate, Chroma, pgvector) without sanitization or source attribution.
  - Activation signals cover Python, JavaScript/TypeScript, Go, Ruby, Elixir, and Java/Kotlin SDKs.
- **Framework-aware rule packs** with three packs shipping at launch (alphabetical):
  - Django/Python — `mark_safe`, `extra`/`raw()` query interpolation, CSRF disabled, `DEBUG=True` in prod, `cleaned_data` mass-assignment.
  - Phoenix/Elixir — `Phoenix.HTML.raw/1`, missing `force_ssl`, `Plug.CSRFProtection` disabled, `Ecto.Query.fragment` string interpolation, LiveView event handlers trusting `phx-value-id`.
  - Rails/Ruby — `html_safe`/`raw()`, `find_by_sql` interpolation, `protect_from_forgery` disabled, `params.permit!` mass-assignment, `eval`/`send`/`instance_eval` with user input.
  - Activation is dual-gate (file extension AND import detection) so polyglot repos route each file to the right pack. Every per-pack rule maps to one of the existing universal `vulnerability_class` values — no per-framework enum proliferation.
  - "Adding a new framework pack" template documented in the agent prompt for contributors extending to Spring, Express, Gin, Laravel, FastAPI, etc.
- **CI/CD pipeline rule pack** covering eight platforms (alphabetical): Azure Pipelines, Bitbucket Pipelines, CircleCI, Drone, GitHub Actions, GitLab CI, Jenkins, Tekton. Five rules apply identically across every platform:
  1. External action / orb / template not pinned to an immutable SHA (`supply_chain`).
  2. Overly-broad permissions or scopes (`insecure_config`).
  3. Untrusted-ref or fork-PR build patterns (`insecure_config`).
  4. Secrets exposed alongside attacker-controlled input (`insecure_config`).
  5. Expression / interpolation injection in shell-step bodies (`injection`).
  - Activation is by file path (`.github/workflows/*.yml`, `.gitlab-ci.yml`, `.circleci/config.yml`, etc.) — generic YAML never triggers.
- **`--maestro` flag** — opt-in 7-layer threat classification using the Cloud Security Alliance MAESTRO taxonomy. Adds an optional `maestro_layer` field to each finding (`foundation-models`, `data-operations`, `agent-frameworks`, `deployment-infrastructure`, `evaluation-observability`, `security-compliance`, `agent-ecosystem`). Renders a `## By MAESTRO layer` summary section after the severity-grouped findings. Omitted entirely when the flag is not set.
- **`--rci [N]` flag** — Recursive Criticism & Improvement. Runs N additional critique-and-refine passes (default 1, clamped to 3) after the initial dispatch. Each pass receives both the prior pass's JSON findings AND the original input, and is asked to drop false positives and surface anything that was missed. `summary.rci_passes` integer records the pass count. OpenSSF documents this technique as reducing security-weakness count by up to an order of magnitude. Cost scales linearly.
- **`--baseline [PATH]` and `--update-baseline` flags** — baseline suppression. Acknowledged findings are filtered from the rendered report and counted in `summary.suppressed_count`. Baseline file schema: `{schema_version: 1, acknowledged: [...]}`. Fingerprint is `SHA256(vulnerability_class | file | line | first_80_chars_of_description)` — stable across runs even when severity or remediation prose changes.
- **`--patches` flag** — auto-remediation diff suggestions. Each finding gains an optional `patch` field containing a `git apply`-compatible unified diff, emitted only when the fix is surgical (1–20 lines, single file, no new deps, no API breaks), unambiguous, and verifiable from the supplied input alone. Most findings won't have a patch even with the flag set — that's the correct output, not a bug.
- **Cross-batch deduplication in full mode.** The merge step now runs an order-stable dedup pass keyed by `(file, line, vulnerability_class)`. Duplicates that surface across batches or RCI passes collapse to the first occurrence. `summary.findings_by_severity` is recomputed from the post-dedup list (not summed from per-batch counters, which drift after dedup).
- **`summary.files_skipped` in full mode** — array of `{path, reason}` records for every file the binary/size filters dropped. `reason ∈ {binary, oversize, unreadable}`. Always emitted in full mode (even as `[]` to prove the filter ran); omitted in diff mode. Human-readable report renders a `## Skipped` block capped at 50 entries with an `... and N more` overflow line.

### Changed

- The `vulnerability_class` enum gains six new values (`supply_chain` plus the five agentic classes). Callers that exhaustively switch on the enum need to handle the new values. Most callers consume the field as an opaque string and are unaffected.
- Full-mode contract: the "do NOT deduplicate" rule from v1.1.0 is replaced by the order-stable dedup pass described above. Diff mode is still a single dispatch where dedup is a no-op, so diff-mode JSON output is byte-identical to v1.1.0 for the same input.

### Notes

- All new flags compose. `--maestro --rci 2 --patches --baseline --full --json lib/` is a valid invocation.
- Cost discipline: `--rci 3 --full` over a 41-batch scan is 164 agent dispatches. The slash command does not warn about this — the trade-off is documented here and in the agent prompt; the user is in control.
